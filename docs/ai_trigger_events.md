# События запуска анализа инцидентов ИИ

В архитектуре системы используется событийная модель (**Event-Driven AI Analysis**): искусственный интеллект анализирует инцидент не по расписанию «раз в час», а **в момент наступления ключевых событий** жизненного цикла заявки. 

Благодаря ультранизкому времени инференса моделей (**менее 0.5 мс** на инцидент прямо в памяти Go-микросервиса), пересчет выполняется синхронно и мгновенно рассылается координаторам через **Server-Sent Events (SSE)**.

---

## 1. Карта триггерных событий

```
[Поступление / Изменение инцидента]
                 │
                 ▼
  Какое событие произошло?
  ├── 1. Регистрация нового инцидента (POST /api/incidents)
  ├── 2. Назначение на координатора (assignedGroupName)
  ├── 3. Изменение приоритета / срочности (priorityId, urgencyId, impactId)
  ├── 4. Дополнение описания / логов аварии (header, description)
  ├── 5. Переход в статус «Исследование ситуации» (state)
  └── 6. Пакетная загрузка / Сидинг базы (Seed / Batch Import)
                 │
                 ▼
  [ml.GetEngine().Evaluate(incident, ctx)]
  └── Единая регрессионная модель (gbdt_reg_v2.0):
      ├── Прогноз длительности T_pred и 80% ДИ [T_min, T_max]
      ├── Риск срыва SLA (SAFE / WARNING / CRITICAL) и запас времени
      └── Ранжирование команд (TF-IDF профили + оценка SLA) и подбор инженера
                 │
                 ▼
  [PostgreSQL: сохранение новых скорингов]
                 │
                 ▼
  [SSE Hub: мгновенная трансляция в браузер координатора]
```

---

## 2. Подробное описание каждого события

### 1. Первичная регистрация инцидента (`INCIDENT_CREATED`)
* **Когда происходит:** Инцидент впервые поступил из внешней системы мониторинга (Zabbix, Prometheus, почта, автоалерты) через `POST /api/incidents`.
* **Что делает регрессионная модель:**
  * Сразу оценивает ожидаемую длительность решения $T_{\text{pred}}$, риск срыва SLA и проверяет соответствие назначенной группы профилю проблемы.
* **Результат для координатора:** Инцидент появляется на дашборде уже обогащенным бейджами риска и рекомендациями.

### 2. Попадание в очередь координаторов (`COORDINATOR_ASSIGNED`)
* **Когда происходит:** Инцидент переведен на группу `«КЦ ИТ Координаторы Массовых Инцидентов»` (ошибочно назначен оператором первой линии, автоалертом или возвращен другой командой).
* **Что делает ИИ:**
  * Запускает TF-IDF векторизацию текста проблемы, названия продукта, сценария и сервиса.
  * Исключает из возможных вариантов саму команду координаторов.
  * Находит наиболее вероятную целевую инженерную группу из 22 команд и ранжирует Top-3 альтернативы.
* **Результат для координатора:** В карточке загорается подсказка: `💡 ИИ: [Команда] [97.8% точность]` и активируется кнопка **«Передать в 1 клик»**.

### 3. Смена приоритета, срочности или влияния (`SEVERITY_UPDATED`)
* **Когда происходит:** Дежурный инженер или система изменили `priorityId`, `urgencyId` или `impactId` (например, инцидент подняли со «Среднего» на «Высокий»).
* **Что делает модель:**
  * Выполняет немедленный пересчёт прогноза длительности $T_{\text{pred}}$ и риска срыва SLA.
  * Если приоритет или риск срыва SLA критический, генерируется событие оповещения.
* **Результат для координатора:** Карточка подсвечивается оранжевым или красным, координатор слышит звуковой сигнал и видит скачок риска в процентах.

### 4. Обновление текста проблемы и технического описания (`DESCRIPTION_UPDATED`)
* **Когда происходит:** В поле `description` или `header` добавлены новые технические подробности сбоя, стектрейсы или уточнения от пользователей.
* **Что делает ИИ:**
  * Сканирует обновленный текст на появление аварийных триггерных слов (*«отказ ядра», «массовые жалобы», «блок», «падение»*).
  * Пересчитывает семантическую близость к профилям команд.
* **Результат для координатора:** Рекомендация команды назначения может скорректироваться, если открылись новые детали (например, выяснилось, что проблема не в софте, а в дисковом массиве SAN).

### 5. Переход в статус «Исследование ситуации» (`RCA_ENTERED`)
* **Когда происходит:** Инцидент технически решен, сервис поднят, но статус переведен в `«Исследование ситуации»` для выяснения коренной причины (Root Cause Analysis).
* **Что делает ИИ:**
  * Проверяет, какая команда должна вести доработку или устранение технического долга по продукту/сценарию, чтобы исключить рецидив аварии.
* **Результат для координатора:** Задача перемещается в 4-ю колонку дашборда и остается под контролем координатора.

### 6. Первичный сидинг и пакетный импорт данных (`BATCH_IMPORT / SEED`)
* **Когда происходит:** При старте сервера или при вызове сброса/импорта из файла `data/character_problems.json`.
* **Что делает ИИ:**
  * В цикле пакетно прогоняет все 44 исторических инцидента через модуль инференса, рассчитывая оценки риска и маршрутизации для каждого из них перед записью в PostgreSQL.
* **Результат для координатора:** С первой секунды запуска дашборда все карточки содержат рассчитанную аналитику ИИ.

## 3. Где это реализовано в коде

1. **Точка вызова анализа в Go:**
   В файле `backend/internal/database/db.go` в методе `UpsertIncident()`:
   ```go
   // Автоматический запуск анализа ИИ при любом сохранении/обновлении
   ml.GetEngine().Evaluate(inc)
   ```
2. **Движок анализа:**
   В файле `backend/internal/ml/engine.go`:
   * `evaluateTeamRoutingWithRegression(inc, ctx)` — ранжирование команд с учётом TF-IDF профилей и регрессионного прогноза SLA.
   * `evaluateRegressionAndSLA(inc, ctx)` — расчёт $T_{\text{pred}}$, 80% ДИ, Топ-3 факторов, риска срыва SLA и подбор свободного инженера.
3. **Рассылка результатов:**
   В файле `backend/internal/api/incidents.go` и `demo.go`:
   После сохранения обогащенного инцидента в PostgreSQL вызывается `sseHub.BroadcastEvent()`, который мгновенно доставляет новые значения на экран дежурного координатора.
